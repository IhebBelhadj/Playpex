## 1. Goal

Split Playpex into **two kinds of products**:

1. **Playpex Media Server**, installed once on an always-on machine:
   - **Self-contained installer**: no Node, ffmpeg or anything else needs to be on the system. The installer ships the runtime, the server, ffmpeg/ffprobe and the dashboard.
   - **Its own executable** ("Playpex Media Server"). Opening it starts the server **in the background**, with no window. A **tray icon** (Windows notification area, macOS menu bar, Linux AppIndicator) shows status and has Open dashboard / Pause / Restart / Quit.
   - **Web dashboard** at `http://<server>:<port>/` in any browser: status, active streams and torrents, connected clients and paired devices, live logs, download directories and storage, settings (ports, sharing, API keys, limits), first-run setup.
   - **Start at login** (Windows/macOS/Linux desktop), and a **headless** edition for Linux boxes/NAS (systemd service, Docker) with the same dashboard (deferred: step 7, §13).
   - **Discoverable on the LAN**; devices pair with it once.
2. **Clients**, installed separately on each device, talking to the server over a **documented, versioned API**:
   - The current Angular + Electron TV app becomes **Playpex TV**, with no server inside it. It finds servers on the LAN, pairs, and streams.
   - Other clients come later (Android TV, mobile, web). Nothing in the protocol may rely on Electron or Chromium: discovery, pairing, auth, streaming and codec choices must all be implementable on any platform.

Non-goals for this plan: access from outside the LAN (NAT traversal, TLS, relay), one client talking to several servers at once, Windows "service" mode that runs before login (§13), the extra clients themselves.

## 2. Today, and what blocks the split

| Concern | Today | Problem |
|---|---|---|
| Packaging | One Electron app = UI + server (`src/electron.js` requires `server.js`) | No server-only product; the server dies with the UI and needs a display |
| Runtime | Electron's Node in prod; system `node` in dev | Headless install needs a runtime on the system |
| Dependencies | One root `package.json` for Angular 14, Electron, and server deps | Can't build a server-only or client-only package |
| ffmpeg | Must be on the PATH (not bundled) | Users must install it themselves |
| Config | `.env` (repo, dev only) + env vars; packaged builds have no way to set API keys | Server settings need a UI (the dashboard) and persistent storage |
| Logs | `console.log` + `morgan` to stdout | Nothing to show in a dashboard; lost when there's no terminal |
| Server URL in the UI | `server-config.ts` const `http://localhost:<?streamer=>`, used by 11 files | Host hard-wired; can't target another machine |
| Exposure | `listen(port)` on all interfaces, CORS `*`, no auth; state-changing `GET` (`/torrents/:hash/deselect`) | Already open to the whole LAN and to any web page today |
| Power API | Unauthenticated express on `:3344` in `electron.js` | Any web page can shut the PC down; belongs to the client device anyway |
| Torrent lifetime | Player `DELETE`s the torrent when leaving | With several clients, one can kill another's stream; a crashed client leaks a downloading torrent |
| Codec decisions | The Chromium player decides (probe → transcode audio if AC-3/DTS) | Each client platform decodes different codecs; the server should decide per client |
| Catalog | TMDB called by the renderer, key in `movies.service.ts` | Every future client would embed the key (§12 G) |

Good news: the server only needs pure-JS dependencies (`express`, `torrent-stream`, `drizzle-orm`, `axios`, `socket.io`, …), and SQLite comes from Node's built-in `node:sqlite`. **There are no native modules to rebuild per platform**, so the server can be bundled with any Node 24 binary.

Principles:
1. **One server core**, run by two thin hosts (desktop supervisor, headless launcher). The core never imports Electron.
2. **The API is the product boundary.** Everything a client needs is under `/api/v1`, described by an OpenAPI spec in `packages/protocol`. No client may depend on server internals.
3. **The dashboard is just another client** of the server (admin routes, admin session). It is served by the server itself, so it works on headless installs and from any machine.
4. **Secure by default**: LAN access needs a paired device or an admin login; no state-changing `GET`; Host-header check against DNS rebinding.
5. **Every step leaves something working**, like the movement-system migration. The all-in-one app kept running until the TV client was separated (step 9, done).

## 5. Server core (`apps/server`)

### 5.1 Lifecycle and entry points
- `index.js` (next to `server.js`) exports `start(options) → Promise<{port, urls}>` and `stop()`. Nothing listens on `require`.
- `bin/playpex-server.js`: headless entry. Reads settings and env, calls `start()`, and on SIGINT/SIGTERM stops gracefully (sends the mDNS goodbye, closes HTTP, destroys engines).
- In the desktop edition the supervisor runs this same entry in a `utilityProcess` and receives status over `process.parentPort` messages (`{type:'status', port, streams, clients, …}`, `{type:'log', …}`).
- Uncaught exceptions are logged and the process exits with a code. The supervisor (or systemd/Docker) restarts it, with back-off.

### 5.2 Data locations
Keep `lib/paths.js` and the existing `Playpex` dirs, so today's `playpex.db` and profiles carry over. Add:
- `logs`: Linux `~/.local/state/Playpex/logs` (headless as a system service: `/var/log/playpex`), macOS `~/Library/Logs/Playpex`, Windows `%LOCALAPPDATA%\Playpex\Logs`.
- `downloads`: default `<cache>/torrent_data`, **configurable** in settings (§5.3).
- Headless system service: `/var/lib/playpex` for config and data (`PLAYPEX_CONFIG_DIR` / `PLAYPEX_CACHE_DIR` already exist).

### 5.3 Settings (`settings.json` in the config dir, edited from the dashboard)
Settings are read before the DB opens: port and download dir are needed first. Env vars override them, which Docker needs. The `.env` file stays a dev convenience only.

| Group | Settings |
|---|---|
| General | server name (default hostname), HTTP port (fixed, default **28470**, §5.9), ~~discovery UDP port (28471)~~ (fixed, step 8 notes), ~~language of logs~~ |
| Network | LAN sharing on/off (bind `0.0.0.0` vs `127.0.0.1`), discovery on/off, allowed CORS origins |
| Storage | download directory (writable + free-space check; torrents already running keep their dir), ~~cache size limit~~ (§14.1), "delete after watching" (today's behavior, default) ~~vs keep for N days~~ |

| Providers | TMDB, OpenSubtitles, Wyzie, ThePornDB keys (masked in the UI, never returned in full by the API); ~~enabled sources per kind~~ |

Struck through = not built (as of step 10): dropped, or waiting for the § named.
| Desktop only | start at login, check for updates (the supervisor owns these; the dashboard toggles them through the admin API → IPC) |

`GET/PUT /api/v1/admin/settings`. Changes that need a restart (port, bind) are flagged in the answer, and the dashboard offers "Restart server".

### 5.4 Logging (`lib/logger.js`)
- `pino` writes JSON lines to rotating files (`pino-roll`: daily rotation, 7 files, 10 MB each) and keeps an in-memory **ring buffer** of the last 2 000 entries for the dashboard.
- Replace `console.log` / `morgan` everywhere with child loggers per area (`torrent`, `provider`, `subtitles`, `ffmpeg`, `http`, `auth`, `discovery`). Requests log `deviceId`, method, path and status, never tokens or keys.
- `GET /api/v1/admin/logs?level=&area=&since=` returns the buffer; the events socket streams new lines live; `GET /api/v1/admin/logs/download` returns a zip of the files, useful for bug reports.

### 5.5 ffmpeg
- Ship ffmpeg + ffprobe per platform in the installer (`resources/ffmpeg/`). They are fetched at build time by `build/fetch-ffmpeg` from pinned **LGPL** builds with SHA-256 checks. LGPL is enough for our use (copy video, native `aac` encoder) and avoids GPL redistribution obligations. Licence texts go in the install dir.
- `lib/transcode.js` resolution order: setting → `FFMPEG_PATH` env → bundled → PATH. The dashboard shows which one is used and its version.

### 5.6 Torrent leases, limits, sessions
- Every client request carries its device (from the token, §6). `POST /api/v1/torrents` and every stream request **acquire or refresh a lease** `{hash, deviceId, lastActivity}`.
- `DELETE /api/v1/torrents/:hash` **releases** that device's lease. The engine and its data are destroyed only when no lease is left, after a 30 s grace period (and only if "delete after watching" is on).
- The client player sends `POST /api/v1/torrents/:hash/keepalive` every 60 s while open, so a paused video doesn't look idle. A **reaper** drops leases idle for longer than the idle timeout. This also fixes today's leak when a client crashes.
- Limits: past `maxTorrents` or `maxTranscodes`, the server answers `503 {error, code:'BUSY'}`.
- **Sessions** = what the dashboard's "Activity" shows: device, profile, title, file, play method (direct / audio transcode), position, torrent speed, peers, progress. Built from leases plus a `POST /api/v1/sessions/progress` the player already almost has: today's `PUT …/progress` resume calls can also update the live session. Admins can stop a session from the dashboard.

### 5.7 Discovery advertiser (`lib/discovery.js`)
Discovery only runs when LAN sharing is on (and `network.discovery`, default on), and discovery errors are logged but never crash the server. Built in step 8: see its notes for what differs (own host name in the SRV record, name probing, sending on every interface).
1. **mDNS / DNS-SD**: advertise `_playpex._tcp.local` on the port actually bound. TXT record: `id=<server uuid> v=<apiVersion> ver=<version> name=<server name>`. Library: `bonjour-service` (pure JS). Android (NSD), iOS (Bonjour) and desktop clients can all browse this natively.
2. **UDP responder** on `28471`, a fallback for networks or Windows setups that filter multicast. A client broadcasts the datagram `PLAYPEX_DISCOVER 1`, and the server answers unicast with JSON `{id, name, port, apiVersion, version}`. Clients always broadcast to 28471. If it is taken on the server, only this fallback is lost: mDNS and manual entry still work, and the dashboard shows a warning.
3. Firewall: on Windows, the system's own "Allow access" prompt appears the first time the server listens on the LAN, with no installer rules (no admin rights, §8.2). On Linux deb/rpm, the post-install opens the ports if `ufw`/`firewalld` is active.

### 5.8 Network hardening
- Bind `127.0.0.1` when sharing is off, `0.0.0.0` when it's on.
- **Host check**: reject requests whose `Host` isn't localhost, a local IP, `<hostname>.local` or a configured name. This stops DNS-rebinding attacks from web pages.
- CORS allow list: the dashboard is same-origin, so it needs none. Allowed are `null` (TV client on `file://`), dev origins, and configured ones. CORS is not used for authorization.
- No state-changing `GET`: `GET /torrents/:hash/deselect` becomes `POST`.

### 5.9 Fixed port, changeable by the user
**28470/TCP** (HTTP: API, streams, dashboard) and **28471/UDP** (discovery). They sit in an IANA range that has never been assigned (28241–28588, checked against the IANA registry on 2026-10-16). They are below the OS ephemeral ranges (Linux 32768–60999; Windows/Hyper-V 49152+ and its excluded port ranges), so outgoing connections never grab them by accident. They are also clear of common neighbours: 9000 (PHP-FPM, Portainer, SonarQube), 8096 (Jellyfin), 32400 (Plex), 27015 (Steam game servers), 28015–28016 (Rust game servers). BitTorrent keeps its own range (6881+).

- **The port is fixed.** The server no longer slides to the next free port (today's 9000 → 9001 behavior is removed), so bookmarks, manually entered addresses and firewall rules stay valid.
- **If the port is taken at start:**
  - The server does **not** serve clients. It logs `PORT_IN_USE` (with the owning process when the OS tells us: `netstat`/`ss`) and enters **recovery mode**: the admin UI only, on an OS-assigned port, **loopback only**.
  - Desktop: the tray turns to the warning state ("Port 28470 is in use") and "Open dashboard" opens the recovery page: *Settings › Network* with the conflict explained and a port field (with a "Check" button that tries to bind it). Saving restarts the server on the new port.
  - Headless: the error and the recovery URL are printed to the log/journal. The port can also be changed without the dashboard: `playpex-server set-port 28480`, the `PLAYPEX_PORT` env (Docker), or editing `settings.json`.
- **Changing the port** (Settings › Network, any time): validated as 1024–65535, not in the Windows excluded ranges (`netsh int ipv4 show excludedportrange`, readable without admin), and free right now. The change applies after a restart, which the dashboard offers.
- **Clients follow automatically**: discovery advertises the actual port, and a paired client stores the server `id` and re-resolves its address/port via discovery when the saved URL fails. Manual entry in clients defaults to 28470 when no port is typed.
- Windows firewall: the allow-rule is tied to the executable, not the port, so changing the port needs no new prompt.

## 6. Protocol for all clients (`packages/protocol`)

The point of this section: **a new client can be written from the docs alone.**

### 6.1 API v1
- Every route lives under `/api/v1/`: torrents and streams too (`/api/v1/torrents`, `/api/v1/torrents/:hash/files/:path` …), not just today's `/api/*`. Old unversioned routes stayed as aliases until the TV client had migrated; removed in step 9.
- One error shape everywhere: `{ error, code }` with stable `code`s (`PAIRING_REQUIRED`, `BUSY`, `NOT_FOUND`, `UPSTREAM`, …).
- **OpenAPI 3.1 spec** (`packages/protocol/openapi.yaml`) is the source of truth. The TS types are generated from it; the server serves it at `/api/v1/openapi.yaml`, and the dashboard renders it at `/docs/reference` next to the prose guide `docs/api/` (`/docs`; `/api/v1/docs` redirects there; step 10). A contract test checks the running server's responses against the spec.
- `apiVersion` is an integer, bumped only on breaking changes. Clients send `X-Playpex-Client: <name>/<version>; api=1`. The server refuses unsupported versions with `426 {code:'CLIENT_TOO_OLD'|'SERVER_TOO_OLD'}`.

### 6.2 Server info (no auth)
`GET /api/v1/server` → `{ id, name, version, apiVersion, minApiVersion, auth: 'pairing', features: { transcode, subtitles: [...], adult } }`. Clients probe this before pairing and after discovery. `id` is a UUID kept in `server.json`. Clients identify the server by `id`, not by IP, so DHCP changes don't break anything.

### 6.3 Pairing and auth (Plex-style "link a device", on Better Auth)
Revision 3 (2026-10-16): auth uses **[Better Auth](https://better-auth.com)** (decision I) instead of hand-written tokens and sessions, and pairing follows **RFC 8628** (OAuth device authorization grant): the client shows a code and the admin approves it, the direction of plex.tv/link. Non-JS clients (Android TV, …) only need RFC 8628 and bearer tokens, both standard.

- **Library setup** (`lib/auth/index.js`): Better Auth with the Drizzle adapter (`provider: 'sqlite'`) on the existing `playpex.db`; its tables (`auth_user`, `auth_session`, `auth_account`, `auth_verification`, `auth_device_code`, written by hand in `lib/db/schema.js` in its field names, migration `0002_auth`). Plugins: `username` (admin login without email; the user row gets a placeholder `admin@playpex.local`) and `device-authorization` (RFC 8628). **No `bearer` plugin** (built differently, step 4 notes): device tokens are checked by our own middleware, so they authenticate none of Better Auth's endpoints. Public sign-up is disabled: the only account is the admin ("owner"), created without a password on first start; the first-run setup gives it a username and password. Its handler is mounted at **`/api/v1/auth/*`** (`basePath`), before the body parsers, for an allow list of endpoints (`device/code`, `device/token`, `sign-in/username`, `sign-out`, `get-session`); others are 404. Better Auth is ESM-only: `require()`d (Node ≥ 22.12 `require(esm)`, verified in Electron 44 and Node 22), on first use. Passwords use its default scrypt hashing; its built-in rate limiter covers sign-in (5/min), codes (10/min) and polling, keyed on the socket address (our middleware sets the header it reads; a client-sent copy is overwritten).
- **Pairing** (RFC 8628):
  1. Client: `POST /api/v1/auth/device/code {client_id, scope}` (JSON or form-encoded) → `{device_code, user_code, verification_uri, verification_uri_complete, expires_in, interval}`. `client_id` names the app (`playpex-tv`, …): public clients, so only its shape is checked (`^[a-z0-9][a-z0-9._-]{1,63}$`), not a list. The user code is 8 characters without ambiguous ones; the admin may type it in any case, with or without a dash. The server keeps who asked (address, `X-Playpex-Client`) on the request row for the admin's list.
  2. The client shows `user_code` and `verification_uri` (the dashboard's `/link` page), plus a QR code of `verification_uri_complete`, then polls `POST /api/v1/auth/device/token` every `interval` seconds (`authorization_pending` / `slow_down` / `expired_token` / `access_denied`, as in the RFC).
  3. The admin approves: on the dashboard's `/link` page (types the code, or picks it from the pending requests, §7), from the tray notification (desktop, §8.1), or with the CLI `playpex-server devices approve <code>` (headless, and the only approval path until the dashboard exists, step 5). Requests expire after 10 minutes (setting).
  4. The token poll answers `{access_token, token_type: 'Bearer', expires_in}` once (the code is consumed). The client then describes itself: `PUT /api/v1/devices/me {deviceId, name, platform, capabilities}` → the `Device`.
- **Devices** = Better Auth sessions created by the device flow, plus a side table `devices (id, sessionId → auth_session ON DELETE CASCADE, clientId, name, platform, client, clientDeviceId, capabilities, address, lastProfileId, createdAt, lastSeenAt)`, inserted by a `databaseHooks.session.create.after` on `/device/token` (same request). Device sessions last a year and slide on use (renewed at most daily), so a device seen within the year never expires; revoke = delete the session (the row goes with it; the next request gets 401) and close its streams. Admin sessions are refused and deleted 30 days after sign-in (our check: Better Auth has one session lifetime).
- **Requests**: `Authorization: Bearer <token>`, or `?access_token=` for media elements that can't set headers (Electron injects the header instead, §10.1). Our middleware (`lib/auth/http.js#requireClient` → `identify`) looks the token up with Better Auth's `internalAdapter.findSession` and accepts it only if a `devices` row names its session. Without a valid token → `401 PAIRING_REQUIRED` (+ `WWW-Authenticate: Bearer`).
- **Admin** (dashboard): username + password, Better Auth's HttpOnly session cookie (signed with the server's secret in `<config>/auth.json`, 0600). Admin routes are `/api/v1/admin/*` and `/sessions`, and accept **only a cookie session that isn't a device's**. Device sessions belong to the admin user, so: (1) a raw device token can't be turned into the (signed) cookie, and admin checks also refuse any session listed in `devices`; (2) without the `bearer` plugin, device tokens authenticate no Better Auth endpoint at all (`get-session` answers null); (3) only the allow-listed endpoints are reachable. Password changes go through our `PUT /admin/password` (signs out admin sessions only; Better Auth's `change-password` with `revokeOtherSessions` would also revoke every device).
- **Loopback** requests are trusted as an implicit "local" device, so a client on the server machine needs no pairing (it still names its device with `X-Playpex-Device` / `?device=` for leases). The Host check and CORS still apply. Setting `security.requirePairingOnLoopback`. ffmpeg / ffprobe reading files through our own routes carry a per-process secret (`&internal=`), so they work with that setting on.
- **Spec**: `openapi.yaml` documents the device flow, `devices/me`, `/admin/*`, `/events`, the admin's sign-in / -out / get-session, `PAIRING_REQUIRED` and `ADMIN_REQUIRED`, and security schemes; the contract test covers the full flow (code → pending → slow_down → setup → sign-in → approve → token → request → describe → revoke → 401, deny → access_denied, password change).
- Profile PINs keep gating profiles inside the client, as today.

### 6.4 Real-time events
`GET /api/v1/events`: one WebSocket (`ws`, plain JSON messages, so any platform can consume it). Topics: `torrent.stats`, `session.*`, `server.status`; admin sessions also get `log`, `device.*`. This replaces the unused socket.io v2 server (`lib/socket.js`). The TV UI's current HTTP polling keeps working; moving it to events is optional.

### 6.5 Playback decision per client (Plex-like direct play / transcode)
Each client declares what it can decode right after pairing (`PUT /api/v1/devices/me`, §6.3), and can update it the same way: `capabilities: { containers: ['mp4','mkv','webm'], video: ['h264','hevc?'], audio: ['aac','opus','mp3'], maxHeight: 1080 }`. A Chromium client can't decode AC-3/DTS; an Android TV with ExoPlayer can.
`GET /api/v1/torrents/:hash/files/:path/playback` → `{ method: 'direct'|'audio-transcode', url, duration, tracks }`. The server takes the decision that the TV player makes today (`probe` → `transcode`), using that device's capabilities. Until this exists, the TV client keeps its current logic; it's step 3b, not a blocker.

### 6.6 `packages/client-sdk`
A small TypeScript SDK used by the TV client and future JS clients: `createClient({baseUrl, token})`, typed calls generated from the spec, `mediaUrl(path)` (adds `access_token` where needed), and error mapping (`PAIRING_REQUIRED` → re-pair flow). Discovery isn't in it, because it needs platform APIs; the protocol constants are.

## 7. Dashboard (`apps/dashboard`)

## 8. Desktop server edition (`apps/server-desktop`)

### 8.1 The executable
- Electron is used **as a supervisor only**: no `BrowserWindow`. The server core runs in `utilityProcess.fork` (Electron's built-in Node 24, so there's no separate Node to ship). The installed app is "Playpex Media Server".
- `app.requestSingleInstanceLock()`: launching it a second time just opens the dashboard.
- **Tray menu**: status line ("Running · 2 streams · 3 devices" / "Stopped" / "Error"), Open dashboard, pending pairing requests ("Living room TV wants to connect · code K7QM-4XPD" → Approve / Deny; a desktop notification appears when one arrives; approving goes through IPC to the admin API), Open downloads folder, Pause all downloads, Restart server, Start at login ✓, Check for updates, Quit. Tray icons per state; Windows `.ico`, macOS template image, Linux PNG (AppIndicator).
- **Start at login**: `app.setLoginItemSettings({openAtLogin, args:['--hidden']})` on Windows and macOS, and a `~/.config/autostart/*.desktop` entry on Linux. The installer turns it on by default (option in the setup).
- On the first launch it opens the dashboard's setup page in the browser.
- **Crash handling**: if the child exits unexpectedly, the supervisor restarts it with back-off (1 s, 5 s, 30 s). After 5 crashes in 10 min the tray shows Error and "Open logs".
- Auto-update via `electron-updater` (GitHub Releases). It never restarts during an active session: it asks in the tray, and the dashboard shows the update.
- macOS: hide the Dock icon (`app.dock.hide()`).

## 9. Headless edition (Linux servers, NAS, Docker)

- **Tarball / deb / rpm**: contains `runtime/bin/node` (the official Node 24 binary, fetched and checksum-verified at build time by `build/fetch-node-runtime`), the server, production `node_modules`, ffmpeg and the dashboard. `bin/playpex-server` runs `runtime/bin/node apps/server/bin/playpex-server.js`. Nothing comes from the system.
- deb/rpm post-install creates a `playpex` system user, data in `/var/lib/playpex`, and a systemd unit `playpex-server.service` (`Restart=on-failure`). The setup URL is printed at the end of the install.
- **Docker**: `ghcr.io/…/playpex-server`, `node:24-slim` + ffmpeg, volumes `/config` and `/downloads`. `network_mode: host` is recommended for mDNS and incoming BitTorrent connections; in bridge mode, clients use the manual address.
- Headless first-run setup: the dashboard setup page is only allowed from loopback. Headless boxes can't open it locally, so the install prints a one-time **setup token** (also in the log) that unlocks the setup page from the LAN.
- Optional later: a single-file Node SEA build instead of `runtime/` + `node_modules`.

## 10. Playpex TV client (`apps/tv`)

### 14.1 What happens to a torrent nobody watches (lib/sessions.js)
Today: when the last lease is released, the torrent **keeps downloading** for the 30 s grace period (the watched file stays selected, and `torrent-stream` downloads a selected file in full even with no reader). Then the engine is destroyed and its data deleted (`storage.deleteAfterWatching`, default on). A client that crashes sends no `DELETE`: downloading goes on until the reaper drops its lease (idle timeout 10 min + up to 1 min until the next pass + 30 s grace, about 11.5 min worst case).

"Stop downloading", "stop all torrent activity" and "free the disk" are three goals, best handled at three moments:

| Action | Downloading | Uploading / peer connections | Memory, sockets | Data | Coming back |
|---|---|---|---|---|---|
| Deselect every file + `swarm.pause()` | stops at once | connections stay; peers can still pull pieces | kept | kept | instant |
| Destroy the engine | stops | stops (no seeding, no tracker/DHT announces) | freed | kept | re-add; pieces on disk are checked again (seconds) |
| Destroy + delete the data | stops | stops | freed | freed | download again from zero |

Proposal to review:
1. **Last lease released → stop downloading at once**: deselect every file and pause the swarm; acquiring a lease again in the grace period resumes it.
2. **Grace period over → destroy the engine** (as today): ends uploads and connections, frees memory, stops counting against `maxTorrents`. A paused engine left alive still seeds, holds ~100 peer connections and announces.
3. **The data is a separate decision.** Deleting it right away is the weak part: resume points in the DB keep the `infoHash`, so "Resume" the next day downloads everything again. Better: a **size-limited cache** (the "cache size limit" setting of §5.3, never built): keep the files after the engine stops, evict the least recently watched torrents past N GB (default around 20 GB), and record kept torrents so they survive restarts. Re-adding a cached torrent only checks the pieces already on disk, so resuming starts almost at once. This would replace the `deleteAfterWatching` default; it belongs with the dashboard's Storage page.
4. **Shorter crash cleanup**: the player already sends a keepalive every 60 s, so `streaming.idleTimeoutMinutes` could drop from 10 to ~3 (10 was chosen so that a paused video doesn't look idle, which the keepalive now covers).

### 14.2 Several clients on one server
- **Season pack, two episodes**: the stream route keeps only the streamed file selected and deselects the others (`lib/api.js`, `files` route). Device A on E01 and device B on E05 of the same pack undo each other's selection and both stall. Fix: select the union of the files the torrent's leases are streaming.
- **Torrent-wide actions**: `pause`, `resume`, `start`/`stop`/`deselect` act on the whole torrent for every device. Make them per lease or admin-only (step 4 left them open to any paired device).
- **Kids profiles and 18+ are UI-only**: any client can call `/adult/*` or another profile's library; profile PINs only gate the UI. Needs server-side rules: which profile a request acts for, kid restrictions enforced on the server, maybe a server-wide "disable 18+" setting.

### 14.2d Found while building step 6 (desktop server)
- **Installer size**: the static LGPL ffmpeg + ffprobe are 142 MB each (284 MB unpacked, ~200–256 MB installers in all). BtbN's shared builds would save ~30 MB compressed but bring `lib/` symlinks and RPATH / DLL layout into packaging; an ffmpeg built with only what we use (copy video, decode audio, `aac` encoder, Matroska/MP4) would be a few MB.
- **macOS ffmpeg**: BtbN builds no macOS; common macOS builds (evermeet, ffmpeg-static) are GPL. Needs our own LGPL build (decision F) or accepting GPL there.
- **Linux tray**: GNOME without the AppIndicator extension shows no icon, and the app then has no visible UI at all (the dashboard still works). Detect it and say so (a notification on start, or open the dashboard).
- ~~**Desktop server next to the TV app**~~ (until step 9; gone: the TV app has no server): whichever started first held port 28470. TV app first → the desktop app shows "Another Playpex server is running" and doesn't serve; desktop first → the TV app uses it (fine).
- **AppImageLauncher** (common on Linux desktops) intercepts the AppImage's first run with an "integrate?" dialog and moves it to `~/Applications`; the autostart entry follows on the next start.
- **Updates and the database**: an update can bring a migration; nothing backs up `playpex.db` first (same as §14.3).
- **electron-builder trap**: `${platform}` in file patterns is the *build* machine's platform; per-target `extraResources` name the directories instead (a cross-built Windows installer had Linux ffmpeg in it).

### 14.2e Found while building step 8 (discovery)
- **mDNS A records list every interface's address** (Docker bridges, VPNs): clients try them all and keep the first that answers `GET /server`. It works, but answering with the address of the network the query came from (what Avahi does) would be cleaner; bonjour-service can't, it would mean our own responder on multicast-dns.
- **IPv4 only**: the UDP responder is `udp4` and the TV client ignores IPv6 addresses (link-local ones need a zone id a URL can't carry well). Fine for home LANs; IPv6-only networks would need it.
- **Firewall rules name the default ports**: after the port is changed in Settings, a ufw / firewalld user must open the new one by hand, and the dashboard doesn't say so. The AppImage has no install step, so no rules at all. Uninstalling deletes `allow 28470/tcp` even if the user had added that same rule before.
- **mDNS through a firewall**: ufw's default policy blocks incoming UDP 5353, so behind an active ufw only the UDP fallback (28471, opened by the deb) finds the server. Opening 5353 is broader than Playpex; left to the user.
- **Windows**: not tested whether the first-listen "Allow access" prompt (and the tray's rule) let mDNS and UDP 28471 in for the utilityProcess; it is the same executable, so it should.
- ~~**The TV app's embedded server advertises itself too**~~ (gone with step 9); two Playpex servers on one machine both answer UDP (shared port) and mDNS (different names or `(<id4>)`).

### 14.2f Found while building step 10 (docs)
- **`session.*` events go to every client**: any paired device's events socket gets the other devices' sessions (device name, address, title, profile id, position), while `GET /sessions` is admin-only. Send a device only its own sessions (or make `session.*` admin-only), and document the change.
- **The probe's `transcode` flag is Chromium's view** ("the default audio track won't play in Chromium"); other clients must decide from `audio[].codec`. Goes away with §6.5's per-device decision; the guide says so meanwhile.
- **Embedded subtitles** (MKV text tracks) aren't extracted by the server: only provider subtitles reach clients. A `/subtitles/embedded` route (ffmpeg → WebVTT) would help every client.
- **API reference size**: Scalar is ~1.9 MB of JS (580 KB gzipped, Vue runtime + its agent / client code) loaded only on `/docs/reference`; fine on a LAN. A lighter renderer (Redoc, or our own from the spec) if it matters.
- **Spec gaps found by the "client from the docs alone" review**: closed `enum`s (`Error.code`, `Session.method`, `ServerInfo.auth`, OAuth errors) contradict "new values don't bump the API version" and break strict generated clients (Kotlin / Swift): mark them open (`anyOf` enum + string) or document per field; no operation declares the answers every route can give (`401 PAIRING_REQUIRED`, `403 HOST_NOT_ALLOWED` / `ORIGIN_NOT_ALLOWED`, `426`, `503 BUSY` in recovery): shared `responses` on each operation, or a documented global set; `DeviceDescription.deviceId` accepts any string ≤ 64 while `?device=` requires `^[A-Za-z0-9._:-]{1,64}$` (validate the same pattern in `PUT /devices/me`); `RateLimited` is `{type: object}` (Better Auth's body), the one 429 shape outside `{error, code}`; `YtsResponse.data` is untyped (movie torrents' `hash`, `quality`… unspecified). The guide documents each one meanwhile.
- **`/docs` is public** (like `GET /server` and the spec): it reveals nothing about the server but that it runs Playpex. Revisit if the server ever faces the internet (§13).

### 14.2g Found while building step 9 (TV client)

- **No Content-Security-Policy** on the TV page (Electron warns in the console). It loads its own files, TMDB images and server media only; a CSP (`default-src 'self'`, `img-src` TMDB + the server, `media-src` the server, `connect-src` TMDB + the server) would need the server's origin at boot: set it from the main process with `onHeadersReceived` on `file://`, or a `<meta>` written by `server-config.ts`.
- **Media errors aren't connection errors**: `ServerErrorsInterceptor` sees `HttpClient` only. A `<video>` / `<track>` request refused with 401 (device revoked mid-film) surfaces as the player's own error, and the app learns about the revocation on its next API call.
- **Finding the installed desktop app** relies on `desktop-app.json`, written on every packaged start; before its first start only the usual install places are tried (Windows: any `%LOCALAPPDATA%\Programs\*\playpex-media-server.exe`; Linux: `/opt/Playpex Media Server`; macOS: `/Applications`). An AppImage that was never started isn't found.
- **Same server under two addresses**: entering this machine's LAN address pairs (the server sees a LAN client), while discovery lists the same server as "This computer" (loopback). Harmless, but the card doesn't say which address is in use.
- **TV app tests**: the step was verified with an offscreen Electron harness driving the real `main.js` (kept out of the repo). Turning it into a committed smoke test (`apps/tv/test/`, with a headless server on its own config dir) would protect steps 4 and 9; see "TV client tests" below.

### 14.3 Features named but not designed
- **Disk space**: no disk-full handling while downloading, no cleanup job; data kept with `deleteAfterWatching` off isn't tracked after a restart (see 14.1.3).
- **Video transcoding**: play methods are only `direct` and `audio-transcode`, while capabilities (§6.5) carry `maxHeight` and `hevc?`. Nothing covers a client that can't decode the video (HEVC without hardware support, 4K → 1080p) or hardware acceleration. Needs a §12 decision on scope.
- **Settings without an engine behind them**: §5.3 lists an upload rate limit and a BitTorrent port range, but `torrent-stream` has no rate limiting. Decide before the dashboard shows them (step 5).
- **Privacy on an always-on machine**: binding BitTorrent to a VPN interface; how long logs that record who watched what are kept.
- **Database backups**: auto-update runs DB migrations with no backup of `playpex.db` first and no downgrade path; no export/backup in the dashboard.

### 14.4 Building and shipping
- **CI**: nothing builds the installers on the three OSes or runs the contract test on each change (steps 6 and 7 rely on it).
- **Windows code signing**: §8.2 covers macOS notarization only; an unsigned NSIS installer gets SmartScreen warnings. Needs a certificate (cost decision).
- **TV client tests**: step 9 is verified by hand and the Karma specs are mostly broken stubs. One Electron smoke test (pick a profile → play a public-domain torrent) would protect steps 4 and 9.
- Small items: the ffprobe cache in `lib/transcode.js` is keyed by URL, which now includes `?device=`, so each device probes the same file again, and it never evicts; a transcode refused with `BUSY` still takes a lease; the phone remote (`apps/tv/electron/remoteWs.js`) isn't listed in §13.
